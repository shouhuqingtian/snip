# 2.0.32：修复 GPU 翻译加载确认误判

## 诊断与原因

用户提供 TITAN X Pascal 12 GB 的任务管理器截图及 2.0.31 诊断包。当前会话三次离线翻译均经过 Vulkan 设备检测，进入 GPU 加载后约 1.59～1.69 秒记录零确认层数、回收工作进程，然后实际由 CPU 完成。设备检测已经通过，本次不能归因为未安装 GPU 运行库或未通过 1536 MiB 可用显存门槛；任务管理器的 3D 利用率不能单独证明翻译后端。

代码把 `llama-server` 启动日志阈值设为 3，却依赖 `load_tensors: offloaded N/M layers to GPU` 确认 GPU 层数。固定 b11612 版本的 `common_log_get_verbosity` 把原生库 INFO 映射为 TRACE（4），阈值 3 会屏蔽这条信号。即使工作进程的健康检查已经通过，应用仍因未读到层数而主动回收并回退 CPU。这是一处可复现的程序错误；诊断包本身没有保留原生输出，不能据此声称已经测得这块显卡的实际加速效果。

对应固定上游源码：

- [日志级别映射](https://github.com/ggml-org/llama.cpp/blob/b11612/common/log.cpp#L548)
- [层加载确认输出](https://github.com/ggml-org/llama.cpp/blob/b11612/src/llama-model.cpp#L1973)

## 修复

- GPU 工作进程使用阈值 4，保留所需的原生库启动确认。
- 标准输出和错误输出均通过有界读取器提取数字确认；支持分段读取和最后一行无换行，超长行丢弃后继续读取。只保存是否收到信号、加载层数，不保存原始控制台内容。
- 区分没有收到确认和明确报告零层；只有层数大于零才允许作为 GPU 推理继续运行，原有设备检测、显存门槛、模型/运行库 SHA256 校验、失败回退及取消回收继续执行。
- 诊断的推理指标增加 `LayerSignalObserved`，与 `OffloadedLayers` 配合判断确认是否丢失。
- 模型、运行库版本和文件摘要保持，无需重新下载权重或 GPU 支持。CPU 与 OCR 的推理参数不变。

## 验证

修复前独立核验 b11612 Linux 原生运行库、Hy-MT2 模型的固定 SHA256，用同一模型强制 CPU 启动进行对比：两个进程健康检查均通过，阈值 3 不出现层确认和 load_tensors 日志；阈值 4 出现 67 行 load_tensors 日志及明确的 `0/33` 层确认。两个工作进程都已回收。这验证日志阈值错误，不冒充实体 GPU 推理。

新增 C# 回归同样启动固定真实推理器，强制 `--device none -ngl 0`，要求旧阈值确实抑制信号、新阈值由产品的读取器收到明确零层信号，两个进程均健康并回收。Windows 使用已校验的 Vulkan 运行库执行相同 CPU 样例，即使 CI 没有 GPU 也能验证启动日志约定；实体 GPU 推理独立记录。

本地完整 Release 构建 0 警告、0 错误；128 项 Core、47 项在线翻译协议、17 项在线 OCR 协议检查通过，新增有界信号读取回归通过。Windows 与最终发布包结果见下文。

## 使用与边界

退出旧版托盘，运行新版，在文字工作台选择离线模型，更多设置中使用“自动”或“优先 GPU”。成功应显示“计算方式：GPU（Vulkan）”，诊断中实际 Vulkan 后端的 `LayerSignalObserved=true`、`OffloadedLayers>0`。模型结束退出仍属正常行为。

本修复针对所有 GPU 后端共用的确认错误。TITAN X Pascal 的实际翻译速度、Yoga 的具体显卡及共享内存表现，仍需分别在用户机器复核；本机/CI 没有这两块实体设备，不能承诺兼容性或加速倍数。已有 CPU fallback 日志中的 `ExitCode=-1` 也可能来自正常主动回收，不能单凭此值认定显卡驱动崩溃。
