# OCR 增强评估

评估阶段按用户确认的“先评估准确率和速度，再接入”执行。下文是独立评估的口径与证据；评估后采用 small 限制放大方案接入应用，见 [2.0.27 增强离线 OCR](2.0.27增强离线OCR.md)。

## 已确认的现状

应用使用 Windows 自带 OCR。自动模式按中文、英语的顺序尝试，但中文结果只要非空就停止；因此“非空”不等于“语言选择正确”。现有小裁图增强也只在结果为空时触发，不能解决非空错字。原生引擎没有在当前服务契约中提供可用的文字置信度，不能假装已经可靠判断所有错字。

历史原生回归主要覆盖英语、小裁图、可复制结果和响应性，对中文字符准确性的覆盖不足。本次不将用户截图、识别原文或诊断包加入仓库，也不向在线服务发送截图。用独立生成的公开产品名、虚构表单标签测试候选方案。

## 对比方法

29 张图：12/18/28 px 中英文、混排、相似字符、三种背景、4K 表单和 4200 px 长图。只忽略空白和全角/半角兼容差异；错字、漏字、漏标点都计入错误。此合成样本用于比较候选，不代表真实场景总体准确率。

Windows 分别测试 Python RapidOCR 和实际准备采用的 C# RapidOcrNet 4.2.0，不能把 Python 性能直接视为应用表现。每个候选在独立进程运行，ONNX 两个 intra-op 线程、一个 inter-op 线程。对每图重复三遍，统计后两遍耗时。进程峰值包含运行时、解码和模型，不是仅模型增量。

检测与识别模型为 PP-OCRv4 mobile、PP-OCRv6 tiny/small。small 另测限制放大的参数档位；它仍是同一个模型。模型 SHA256 与固定提交的 RapidAI 官方清单一致，读取前校验。模型大小只统计检测+识别权重，运行组件和未使用的方向分类权重另计。

## 已有实测结果

Linux 探索性测试中，small 默认参数的普通裁图连续耗时中位数约 480 ms；限制小图放大后降至 67 ms。完全一致样例从 24/29 增至 26/29，剩余三例为刻意加入的 I/l 相似字符。限制放大后的普通裁图进程采样峰值约 226 MiB，整组图片峰值约 663 MiB。

最小 tiny 模型约 6 MiB，速度更快，但在 Noto CJK 字体下反复出现常见中文字符错误。限制放大后仍为 21/29 完全一致；不能因为下载小就默认采用。

Windows 第一轮默认参数测试中，C# tiny 为 24/29，small 为 23/29；整组进程峰值分别约 802 MiB、1059 MiB。说明模型名字更大、更先进都不等于实际效果一定更好，默认预处理也不适合直接接入轻量截图软件。

该 Windows 环境只有 en-US 原生 OCR：英语 15 张中 12 张完全一致，中文 14 张 **Unrun**。这些数据不能用来声称已经测得相对于原生中文 OCR 的提升幅度，也没有复现用户原始截图。

Windows 第二轮同机比较：small 默认参数 23/29、普通裁图连续中位 1177 ms、整组峰值1063 MiB；限制放大后为 26/29、中位118 ms、整组峰值599 MiB，普通裁图测量结束时工作集最高151 MiB。初始化至第一张图结果386 ms，不含进程启动和传输。剩余三例均为专门加入的相似字符 I/l/1 测试，其他中英标签、单词和长图在该测试中一致。

## 接入建议与剩余工作

采用 **PP-OCRv6 small + 限制小图放大**，检测+识别权重合计 31,163,977 字节，约 29.72 MiB。该方案已通过 Windows 优化参数对比。

建议增强识别作为可选组件，保留原有免下载 Windows OCR。首次下载组件时显示真实大小，校验模型和运行文件；不在托盘启动时加载。优先采用独立识别进程，限制 CPU 线程，操作结束退出，使取消、超时或引擎故障不会带走主程序，也不会在空闲时保留模型工作集。实际冷启动还须计入进程启动和图片传输，不能只引用推理时间。

长图/4K 仍须研究按块识别与坐标归并，以控制大图峰值；不能从“小图更快”推断所有截图都低占用。真正接入还要验证结果窗口响应、取消、重复截图资源回收、引擎缺失回退、下载失败反馈和模型许可交付。对不确定字符应便于核对原图，不采用针对单词或用户文本的硬编码替换。

## 修改文件

- `tools/ocr-evaluation/evaluate.py`：生成公开合成图片、固定模型校验、独立 Python 进程测量、限制放大对照和 JSON 明细。
- `tools/ocr-evaluation/models.json`：固定模型来源、六个权重的官方 SHA256、PyPI 模型数据包校验和镜像。
- `tools/ocr-evaluation/requirements.txt`、`.gitignore`：仅评估使用的 Python 依赖；排除生成缓存。
- `tools/ocr-evaluation/NativeBenchmark.csproj`、`Program.cs`：独立的原生 Windows/C# 引擎基准；不加入应用依赖图。
- `tools/ocr-evaluation/README.md`：复现步骤、统计口径、下载与内存边界。
- `.github/workflows/ocr-evaluation.yml`：真实 Windows 基准与证据归档；成功只表示测量完成，不表示所有识别样例正确。
- `.github/workflows/inspect-validation.yml`：支持读取已归档的 OCR 评估摘要，避免云环境无法下载 Actions 附件时重跑整组测试。
- 本文：结果、验证边界与接入建议。本评估工具不加入应用依赖；随后应用接入的修改文件单列在 2.0.27 变更记录中。
