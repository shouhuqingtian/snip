## 3. 必须明确的交互

### 3.1 主截图流程

已确认：选区形成后显示浮动工具栏，直接在选区里标注；独立编辑窗口保留为可选入口。

工具栏需适应显示器边缘、负坐标和混合 DPI，并避免挡住用户正在绘制的区域；导出图片不含工具栏及遮罩。

绿色对勾建议定义为“合成截图、复制到剪贴板、关闭截图遮罩并返回原应用”。保存按钮建议只负责另存为，不隐式取消编辑；这些行为待用户确认。

文字建议直接在图像位置输入和修改；颜色、线宽、字号采用对应工具的浮动属性面板。是否采用这些行为待确认。

### 3.2 OCR 与翻译

- 已确认：OCR 和翻译均使用可配置在线服务。
- 仍需确认服务提供方、识别语言与翻译来源/目标语言。不能用未配置的接口或固定文本充当翻译功能。
- 若选择 OpenAI 兼容接口，OCR 所选模型必须支持图像输入；翻译模型可独立配置。若选择专用平台，则按该平台正式 API 适配，不将聊天模型请求直接发给不兼容的 OCR 接口。
- 需要在线服务时，先确认具体服务与配置方式；用户在设置界面安全填写凭据，不在聊天中发送密钥。
- 图片或识别文本是否传给在线服务，需要在相应功能操作中说明，并仅在用户主动触发后执行。
- 识别/翻译的结果窗口提供复制、失败提示和取消，不仅添加一个工具栏图标。

### 3.3 长截图

已确认采用自动滚动：软件驱动目标窗口滚动并采集，需要明确支持的应用、滚动容器、到底检测和异常退出策略。本轮不以手动滚动替代自动滚动功能。

应确认优先支持浏览器网页还是普通桌面窗口，以及固定顶部/底部区域如何处理。不得将普通多张图片纵向堆叠称为已实现可靠滚动拼接。

### 3.4 贴图、表情和分享

- 贴图基础行为建议为桌面置顶显示、拖动位置、滚轮缩放、Esc/右键菜单关闭；透明度及鼠标穿透作为可选择的补充。
- 表情需确认使用内置通用表情还是支持用户导入图片；不复制微信专有素材。
- 分享需要区分 Windows 系统分享面板与直接向微信联系人发送。当前应用与微信没有账号或联系人连接，不能将二者视为同一功能，也不能通过未经确认的模拟点击实现发送。

## 5. 确认后的实现原则

- 延续 C#、WPF、.NET 8、MVVM 和现有 Core / Infrastructure / App 分层。
- 复用已有标注模型、渲染和撤销历史；选区编辑与独立编辑共享同一文档，不维护两套结果不一致的实现。
- 新增 OCR、翻译、长截图、贴图和分享服务，按确认方案注入；不添加虚假的可用入口。
- 每完成一个功能记录修改文件、验证结果及限制。
- 完成后生成新版源码、便携包和安装包，通过现有 GitHub 仓库下载目录交付；版本号随实际新增范围更新。
- Linux 继续执行构建和核心测试；Windows 相关检查及用户实机反馈分别记录，不将编译通过视为桌面交互验收通过。
