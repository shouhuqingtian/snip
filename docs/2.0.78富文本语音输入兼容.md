# 2.0.78 富文本语音输入兼容

用户在 Codex Windows 桌面客户端先聚焦输入框，识别成功却只能手动复制。诊断包尚未收到，不能仅凭截图确定该客户端的所有判定条件。

已在真实 Windows / Chrome 复现同类缺陷：[41990401456](https://github.com/shouhuqingtian/snip/actions/runs/41990401456)，提交 `6e9fff4`。普通 textarea 和带 textbox 语义的 contenteditable 均成功；没有 textbox 角色、内部带段落的富文本编辑器失败。日志显示录音前后控件都可访问、原生焦点未变，但两次 Editable 均为 false，因此没有自动输入。未通过删除字段身份、焦点或密码保护绕过此失败。

## 修改

- `VoiceWorkers.cs`：在 ValuePattern 不可用时，通过 UIA TextPattern 的 IsReadOnlyAttribute 判断富文本是否明确可编辑。只读取该布尔属性，不读取 DocumentRange 的文字；混合/未知属性仍拒绝。保留控件可用、可聚焦、密码状态与每次重新查询。
- `BrowserHoverHitTest.cs` / `VoiceWorkers.cs`：真实 Electron 38 默认启动、真实点击后，现代 UIA 仍可能只返回 Pane，但 MSAA 已返回 ROLE_SYSTEM_TEXT 和 FOCUSED / FOCUSABLE。仅在此种明确的原生文本焦点下使用 MSAA，检查不可用、不可见、离屏、只读和密码状态；通过标准 IAccessibleEx.GetRuntimeId 获取稳定控件身份来区分字段，不使用可能变化的 COM 代理对象指针。仅保留本次使用哪种焦点协议的状态，不记录输入内容，不保存到磁盘。后续查询仍读取最新原生焦点；不能确认时不退化为按窗口身份输入。
- `VoiceInputController.cs`：保留同进程、同 RuntimeId、原生焦点和输入活动检查。诊断增加纯技术属性：控件类型、可聚焦、文本只读状态，以及身份分别是否一致；不写控件文本、名称、ID 值、窗口标题或地址。
- `VoiceInputStatusWindow.cs`：结果保留提示改为“未自动输入，结果已保留”，不把所有无法确认的情况都称为“输入位置变化”。
- Windows 检查增加普通/语义/无角色/纯文本四类 Chromium 编辑区域，真实 Electron 桌面窗口，以及只读、密码不上传、识别期间切换字段的反向检查。使用合成音频与本地假 ASR，不调用付费平台。
- `PrepareElectronFixture.ps1` 和工作流：使用官方 Electron 38.0.0 Windows x64 公开运行时，SHA-256 固定为 `950591d9f3f97700973d5b594ae3833728192b9efd32b94be4d44ca0ef435e40`。仅用于测试，不附带在用户安装包；不强制开启渲染器无障碍开关来掩盖正常启动行为。`Validate.ps1 -Scope Desktop` 在 Windows 自动准备该测试依赖。

## 验证与边界

本地 Release 构建 0 警告 / 0 错误；209 Core、12 HTTP 同步、47 翻译、17 OCR、21 AI 发音、36 ASR 协议检查通过。Windows 与 Electron 实测、完整安装包验证仍待完成。

调查中的真实 Windows 运行 41991088745、41991485331、41991926632、41992339384、41993026129 均保留失败断言：UIA 富文本修复后 Chrome 已通过；Electron 的默认 DOM autofocus 与真实鼠标点击都不能使现代 UIA 暴露编辑器。原生焦点查询随后确认 role=42、state=1048580（文本、已聚焦、可聚焦），但现代 UIA 仍是 type=50030（Pane）、不可聚焦。官方桥接 API 也未解决该差异，最终树已删除该无效桥接调用。增加真实 Electron 同框重复查询身份稳定、不同框身份不同的独立原生回归，不能以移除身份保护通过测试。

这不是对所有应用的无条件注入：不能验证可编辑、原输入控件已更换、密码/只读、用户改变输入位置时继续保留结果。未实际运行用户的 Codex 版本，不能声称已验证该特定版本；管理员权限、应用自定义控件和 UIA 提供程序行为仍可能影响输入。
