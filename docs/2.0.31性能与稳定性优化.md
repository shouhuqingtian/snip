# 2.0.31：性能、冗余与稳定性检查

本轮审查截图编辑、撤销/保存历史、文字工作台及在线请求链路，优先修复能够从代码和回归确认的问题。不是对整台电脑占用或所有场景延迟的统一降幅承诺。

## 修复和优化

1. **释放被淘汰的已保存标注快照**。原先保存状态通过强引用指向整份标注快照；删除贴纸，再超过 100 步撤销历史后，旧快照仍可能持有图片。现在只记录单调递增的版本号，保留原有 100 步撤销、重做和保存状态判断；分支替换不会误判为已保存。没有加入运行时强制 GC。
2. **排版空格不再挤占翻译额度**。增强 OCR 的原文显示、编辑和复制保留列间距与换行；仅翻译副本压缩横向连续空格/制表符、去掉每行首尾排版空格，保留原有换行、空行及字词顺序。覆盖在线、离线模型和基础词典。系统/在线 OCR 原文保持原有提交行为。
3. **识别字数不再计算排版空白**。统计非空白 Unicode 字符，避免把几千个列间空格算作几千字，也不把一个扩展汉字或表情按两个 UTF-16 单元计数。修改原文时更新缓存，界面读取摘要不反复扫描文本。
4. **旧翻译结果保护**。等待翻译期间原文仍可编辑；如果原文已经改变，旧请求的结果不覆盖现有译文，并提示重新翻译。检查覆盖可用性准备和结果返回两个阶段。
5. **在线翻译不再把截断内容当完整结果**。服务明确返回长度上限、内容过滤、工具调用等未正常完成状态时显示提示，保留已有译文；服务拒绝或响应流读取失败也给出可恢复提示，不展示服务商错误正文。
6. **清理在线响应读取的重复逻辑**。在线 OCR 与翻译共用有界 JSON 读取和连接池，仍限制响应 1 MiB、60 秒截止、不自动重定向/重试/切换服务。解析直接使用已读取的缓冲区，减少一次完整响应数组复制。OCR 与翻译的请求内容和密钥仍分别放在各自请求中。

## 验证记录

- 修复前，新增回收测试确认被撤销历史淘汰的已保存贴纸标注仍存活；修复后，同一测试通过。公开合成贴纸使用 4 MiB 数据，测试中显式 GC 只用于验证可回收性，不进入产品流程。
- 已增加保存后撤销再分支编辑的回归，防止用列表下标替代身份而误判保存状态。
- 排版样例原文超过 12000 字符，整理后的翻译副本不足 200 字符，换行、空段和字词保留；原文对象不改写。
- Windows 检查会在实际文字窗口覆盖上述排版样例的自动翻译、复制原文、摘要显示、等待期间修改原文和随后重新翻译。
- 本地完整 Release 构建 0 警告、0 错误；128 项 Core、47 项在线翻译协议、17 项在线 OCR 协议检查通过。
- Windows 最终验证结果完成后补充；未运行的桌面检查不标为已验收。

## 仍然存在的开销

实际可见的高分辨率截图、仍在撤销范围内的标注、可见贴图和约定的恢复缓存需要保留。离线翻译仍需加载约 951 MB 模型，已经采用按需子进程、结束回收，无法靠这轮清理变成轻量词典；基础词典或在线翻译适合更低本机推理负担。增强 OCR 保持约 31 MiB 模型，无需重新下载。没有增加常驻推理、后台轮询或自动联网回退。
